# Progress: decisions

**Status:** published directly, without a Lab step (2026-10-16, built from the roadmap note "A bar or ring that shows how far along a task is"). The page opens on "Bar and ring": a bar and a ring at 64%, and both indeterminate, named underneath, with a Run button at the top right that steps the value from 0 to 100. Examples: With a label, and Ring sizes. The index card shows a bar and a ring (`preview.card`).

- **What it is:** how far along a task is, as a bar or a ring, with an indeterminate state for both.
- **API:**
  - `Progress`: shadcn's, on Radix Progress (`value`, `max`, `getValueLabel`). Unlike shadcn's, it passes `value` on to Radix, so `aria-valuenow` is right.
  - `ProgressRing`: the same props as a ring, plus `size` (`sm | md | lg`: 20, 40 and 64px) and `showValue` (md and lg). It's a separate component rather than a `variant`, because its sizes and value label don't apply to the bar.
  - `ProgressValue`: the percentage as text, for beside a bar (the ring uses it for `showValue`). `aria-hidden`, since the progressbar already says its value.
  - `value` null or left out means indeterminate (Radix's rule). Values outside 0 to `max` are clamped rather than refused (Radix would log an error and drop them), and a `max` of 0 or less falls back to 100.
- **Accessibility:** Radix gives `role="progressbar"`, `aria-valuemin/max/now` and `aria-valuetext` ("64%"), and `data-state` (`loading`, `complete`, `indeterminate`). Every progressbar needs a name (`aria-label` or `aria-labelledby`); the With a label example uses a visible label and a hint (`aria-describedby`). There's no APG pattern for progress bars, so the meta has no pattern link.
- **Look:** neutral. Bar: `h-2 rounded-full`, track `bg-primary/20`, fill `bg-primary` (shadcn's). Ring: `text-primary` with a track at 20% opacity, a round-capped arc starting at the top, and stroke widths set per size on the 24-unit drawing (about 2.5, 3.3 and 4px), so a bigger ring isn't a heavier one.
- **Motion** (`.agents/rules/motion.md`):
  - **A new value rises continuously, not in parts** (owner, 2026-10-21): the bar's fill is moved, not resized (a full-width fill slid with `translateX`), and the ring's arc draws (`pathLength`), both on motion. Each change takes as long as the gap since the change before it, at an even (`linear`) pace, while the gaps stay under `duration.slower * 2` (1s), so updates that keep coming (an upload reporting every 0.7s) join into one smooth rise and the fill never stops to wait for the next step. A change after a longer pause eases in on its own (`duration.slow`, `ease.out`), as it did before. One hook (`useFollow`) times the bar, the ring and the value, so they move together. Never a spring: its overshoot would show more than was done, and past 100 at the end. It used to be a CSS transition (`duration-slow`, `ease-out`) per step, which slid and then stood still: the owner saw it rise in parts.
  - **At 0** the ring's round cap would still draw a dot, so the arc's opacity goes with its length (Checkbox's trick).
  - **Indeterminate:** a segment 40% of the track wide sweeps across the bar (from just off the start to just off the end, `duration.slower * 3`, `ease.inOut`, repeating); a quarter arc turns round the ring (`duration.slower * 3`, linear, calmer than Spinner's one turn a second). Both animate a `transform` string, which motion hands to the Web Animations API (Spinner's approach), so they keep moving while the main thread is busy. The ring turns inside the still root, so no transform lands on the SVG.
  - **Indeterminate with reduced motion:** the sweep and the turn stop; the segment (centred) or the arc pulses its opacity, as Spinner does. A pulse was chosen over a still segment because a still segment reads as a value.
  - **ProgressValue counts** (2026-10-21, with the continuous rise): it counts through every whole number in step with the fill (12, 13, 14 …), on the same timing, a motion value rounded as it goes. A deliberate exception to motion.md's "never a tween through every number": here the number is the bar read aloud, and a per-digit roll (each place swapping through the blur, as before) couldn't keep pace with a fill that never stops.
  - **Switching between indeterminate and a value** jumps to the new state rather than morphing; it's rare, and a morph would need the sweep's position.
- **Demos:** the hero's Run starts an interval in a click handler (no timers at render), stepping through fixed values every 700ms, and clears it on unmount.
- **Tests:** a named progressbar with its value, state and fill offset; a new value; a change lasting until the next one comes (the fill still moving between two updates); `max` and clamping; indeterminate has no value and sweeps; the pulse with reduced motion (the hook stubbed); the ring's value, its size, no value when small, and its turn; ProgressValue counts to the new number and shows nothing without a value; axe.
- **Not built yet:** right-to-left (the fill slides from the left), a striped or buffered bar, sizes for the bar (use `className`, for example `h-1`), a stepped or segmented bar, and a label inside the bar.
